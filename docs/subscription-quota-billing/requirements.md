# 订阅额度计费需求文档

## 1. 目标

在保留现有按 Token 计费能力的基础上，增加按订阅额度计次的计费模式。

普通用户继续使用余额，并按照输入、输出、缓存和思考 Token 计算费用；订阅用户在订阅额度范围内调用指定模型时，只消耗订阅次数，不扣除余额。订阅额度耗尽后，根据配置决定是否回退到余额并按 Token 计费。

## 2. 业务示例

用户购买 100 CNY 的订阅套餐后，获得一个订阅周期内的模型额度：

| 外部模型 | 周期额度 |
|---|---:|
| `5.6luna` | 200 次 |
| `5.6terra` | 80 次 |
| `5.6sol` | 70 次 |
| `5.6` | 30 次 |

上述次数是整个订阅周期的总次数，不是每日次数。

## 3. 订阅周期

- 订阅有效期固定为 30 天。
- 周期从订阅订单审核通过并生效的时间开始计算。
- 订阅到期时间为生效时间加 30 天。
- 每个订阅周期拥有独立的模型额度。
- 周期结束时未使用的次数不结转。
- 提前续费时，新的 30 天从当前订阅到期时间开始顺延，避免损失剩余有效期。
- 续费后的新周期重新获得完整额度。
- 订阅过期后不能继续消耗订阅额度。

## 4. 计费模式

系统保留两种计费模式：

### 4.1 余额 Token 计费

适用于未订阅用户、未配置订阅额度的模型，以及订阅额度耗尽后允许余额回退的请求。

- 请求前按估算费用预扣余额。
- 请求成功后按照实际 Token 用量结算。
- 请求失败、上游重试失败或未产生有效响应时释放/退回预扣金额。
- 输入、输出、缓存和思考 Token 的现有计费逻辑保持不变。

### 4.2 订阅按请求计次

适用于有效订阅且目标外部模型仍有剩余额度的请求。

- 每个成功请求消耗 1 次。
- 请求的 Token 数量不影响订阅次数消耗。
- 订阅额度内的请求不扣余额。
- 请求失败时不消耗次数。
- 内部模型重试只计最终成功的一个请求，不重复扣次数。
- 流式响应已经开始返回有效内容后，即视为一次已使用请求；客户端中途断开不退回次数。
- 管理员发起的模型连通性测试不消耗用户订阅额度。

## 5. 额度回退规则

每个订阅模型额度需要支持 `allow_balance_fallback` 配置：

- 开启：订阅额度耗尽后，继续按余额 Token 计费。
- 关闭：订阅额度耗尽后直接拒绝请求，并返回明确的额度耗尽提示。
- 用户没有有效订阅时，直接使用余额 Token 计费。
- 目标模型没有配置在套餐中时，按余额 Token 计费或按照全局策略拒绝。

建议默认开启余额回退，以保持现有用户行为兼容。

## 6. 模型标识

订阅额度绑定外部模型名，而不是底层 provider 模型 ID。

例如：

```text
订阅模型：5.6luna
底层模型：由当前 external model targets 路由到一个或多个 provider/model
```

更换底层 provider、CLIProxy 实例或 fallback source model 时，只要外部模型名不变，订阅额度仍然有效。

## 7. 数据模型要求

现有每日订阅额度表和 `daily_request_limit` 语义保持不变，不得直接改成周期额度。

建议新增以下概念：

### 7.1 套餐模型周期额度

```text
subscription_plan_model_quotas
- plan_id
- external_model_name
- period_request_limit
- updated_at
```

`period_request_limit = 0` 表示该模型不限量；是否允许不限量需要受管理员权限和产品策略控制。

### 7.2 订阅周期

每次订阅生效或续费生成唯一周期记录：

```text
subscription_periods
- id
- username
- plan_id
- starts_at
- expires_at
- status
- created_at
```

周期记录用于区分同一用户同一套餐的不同 30 天周期。

### 7.3 周期额度使用计数

```text
subscription_period_usage
- period_id
- username
- external_model_name
- used_count
- inflight_count
- updated_at
```

主键应包含 `period_id + external_model_name`。

### 7.4 周期额度预占

```text
subscription_period_reservations
- request_id
- period_id
- username
- external_model_name
- status
- created_at
- completed_at
```

预占必须具备唯一请求 ID，保证重试、重复回调和并发情况下不会重复计数。

## 8. 请求处理流程

```text
识别用户与外部模型
        |
检查有效订阅周期
        |
检查该模型的剩余周期额度
   |                    |
有额度                 无额度
   |                    |
原子预占 1 次          按回退策略处理
   |                    |
转发上游请求       余额 Token 计费 / 拒绝
   |
成功：消耗 1 次
失败：释放预占
```

预占和剩余额度检查必须在数据库事务中完成，避免并发请求突破额度上限。

## 9. 管理员面板

管理员可以：

- 创建和编辑订阅套餐；
- 设置套餐名称、说明、价格和有效期；
- 为每个外部模型设置 30 天周期额度；
- 设置额度耗尽后是否允许余额回退；
- 查看每个用户的当前订阅周期；
- 查看每个模型的已用、剩余和预占次数；
- 手动批准、拒绝和处理订阅订单；
- 续费时明确显示新周期起止时间。

已有每日额度配置应与周期额度分开显示，避免管理员误以为两者含义相同。

## 10. 用户面板

用户可以：

- 查看可购买套餐及价格；
- 提交订阅订单并查看订单状态；
- 查看当前套餐、生效时间和到期时间；
- 按模型查看额度明细，例如“已用 37 / 200，剩余 163”；
- 查看额度耗尽后的余额回退策略；
- 查看订阅历史和续费记录。

用户面板不得展示 provider API Key、CLIProxy auth 文件内容或其他敏感配置。

## 11. 统计与账单

- 订阅请求仍然写入请求记录和统计事件。
- 请求记录需要明确标记 `accounting_mode = subscription`。
- 订阅请求的 Token 使用量继续记录，便于管理员分析成本，但不从用户余额扣除。
- 余额 Token 请求继续标记为 `accounting_mode = balance`，并记录实际美元费用。
- 订阅额度消耗应能按用户、周期、模型和时间查询。
- 历史余额账单不回算、不重写。

## 12. 异常与边界

- 订阅过期后不能预占新额度。
- 额度恰好用完时，只有成功抢到最后一个预占名额的请求可以使用。
- 上游失败时必须释放预占，否则会造成额度永久损失。
- 外部模型被禁用或删除时，历史使用记录仍需保留。
- 套餐模型额度被修改后，不应影响已经生效的订阅周期；已生效周期应保存额度快照。
- 续费审批必须幂等，重复审批不能生成多个相同周期。
- 服务重启后，超过超时时间的进行中预占需要能够清理并释放。
- 数据库写入失败时，不能向用户返回“额度已消耗”的成功结果。

## 13. 兼容性要求

- 未订阅用户的现有 Token 计费行为不变。
- 现有充值、余额、退款和 Token 价格配置不变。
- 现有每日订阅限额功能保留，不与周期额度混用。
- 现有 API 请求格式不变，用户不需要增加新的请求参数。
- 外部模型名称仍使用当前模型目录中的稳定名称。

## 14. 测试验收标准

至少覆盖以下场景：

1. 订阅生效后，四个模型分别按照独立额度计数。
2. 一个请求只消耗目标模型 1 次，不影响其他模型额度。
3. 并发请求不能超过模型周期额度。
4. 请求失败不消耗额度。
5. 内部 fallback 重试最终只消耗 1 次。
6. 订阅额度耗尽且允许回退时，按 Token 从余额扣费。
7. 订阅额度耗尽且禁止回退时，请求被拒绝。
8. 订阅到期后不能继续使用旧周期额度。
9. 续费生成新的 30 天周期和完整额度。
10. 提前续费从原到期时间顺延，不损失剩余时间。
11. 订阅请求写入统计但不减少用户余额。
12. 普通余额请求继续按 Token 正确扣费。
13. 流式成功、流式失败和客户端中断行为符合计费规则。
14. 重复订单审批、重复结算和服务重启不会重复扣次数。

## 15. 实施顺序

1. 新增数据库表、索引和周期额度快照迁移。
2. 扩展订阅仓储层，实现周期额度查询、预占、完成和释放。
3. 扩展订阅服务，接入 30 天周期逻辑。
4. 调整代理请求流程，保留现有余额 Token 计费分支。
5. 增加管理员套餐额度编辑界面。
6. 增加用户订阅和额度展示界面。
7. 增加服务层、仓储层和端到端测试。
8. 在开发环境验证后，再执行生产数据库迁移和部署。
